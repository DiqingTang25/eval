本平台由三个核心组件构成：

MySQL 数据库MySQL RDS (火山引擎)mysql877b303b0151.rds.ivolces.com:3306持久化所有评测数据，11 张业务表 + Token成本追踪
数据流向 (v3.3)：
用户操作前端 → 前端发请求 → [速率限制] → [指标采集] → FastAPI 处理 → [缓存查询] → 缓存命中则直接返回，未命中则读 MySQL → [Token追踪] 写入

2. Adminer — 数据库可视化工具

2.1 这是什么？

你提到的地址：

http://124.174.108.70:8080/?server=mysql877b303b0151.rds.ivolces.com&username=agent_eval&db=agent_eval

这是一个 Adminer（轻量级数据库管理工具，类似 phpMyAdmin），部署在你的实训平台服务器上。它的作用是：

  • 可视化浏览 MySQL 中的所有表和行数据，替代命令行 mysql>
  • 直接查询 任意 SQL 语句
  • 快速验证 数据是否正常入库（比如你之前验证的 persona_smoke 会话）

2.2 URL 参数含义

参数值含义
servermysql877b303b0151.rds.ivolces.comMySQL 服务器地址（火山引擎 RDS）
usernameagent_eval登录数据库的用户名
dbagent_eval默认选中的数据库名
tablealembic_version打开后默认显示的表（这是 Alembic 迁移版本记录表，只有 1 行 1 列，记录了当前数据库 schema 的版本号）

2.3 与前端的关系

Adminer 是「只读查看器」，不参与任何数据写入。它与前端的关系是：

👤 用户操作前端页面 → 📡 后端 FastAPI 处理 → 💾 写入 MySQL
👤 用户打开 Adminer → 🔍 查看 MySQL 中刚才写入的数据

Adminer 读到的每一行数据，都来自前端的某次操作。它让你能"看见"数据库里到底存了什么。

3.8 Agents + WebSocket + Health

端点协议参数返回内容 / 行为
GET /api/agents HTTP 无 [{ id: "platform", name: "HiAgent API测试", type: "api", phases: [...] }, ...]

· scenario_start — {index, total, qa_id} → 场景开始
· response — {turn, status, duration, text} → Agent 回复
· score_done — {overall, correctness, relevancy, ...(8维)} → 评分完成
· done — 评测全部完成
· error — {message} → 异常

GET /health HTTP 无 {"status":"ok","version":"3.2.0"}
Docker 健康检查每 30s 一次（curl），连续 3 次失败则重启容器
WebSocket 事件与数据库时序：WebSocket 推送的事件和 MySQL 写入是同步的——每个事件推送时，对应的数据库写入已经完成。
例如：收到 score_done 事件时，eval_scores 表已经写入完毕，可以立即在 Adminer 中查询到。

4. 11 张 MySQL 表完整详解

以下按数据产生的逻辑顺序，逐一说明每张表的用途、每一列的含义、以及数据是谁/什么时候写入的。

3.1 qa_pairs — QA 黄金问答对

用途：存储评测用的"标准问题 + 标准答案"。评测时从这张表随机抽取问题去问 Agent，再用 Agent 的回答和 golden_answer 对比打分。

列名类型标签含义数据来源
idCHAR(36)PK 内部主键，UUID v4系统自动生成
qa_idVARCHAR(64)UNIQUE 业务标识，如 PHASE01_001QA 生成器按规则生成
phaseVARCHAR(16)INDEX 所属课程阶段：PHASE 01 ~ PHASE 05Excel 源文件决定
typeVARCHAR(32)INDEX 题型：概念解释 / 操作步骤 / 对比分析 / 应用场景Excel 源文件决定
difficultyVARCHAR(16) 难度：简单 / 中等 / 困难，默认"中等"Excel 或人工设定
questionTEXT 问题全文，发给 Agent 的问题Excel 或 LLM 生成
golden_answerTEXT 标准答案全文，Judge 评分的参照基准Excel 或 LLM 生成
knowledge_pointsJSONJSON 知识点列表，如 ["ADC分辨率","ESP32-S3"]Excel 或 LLM 提取
goalTEXT 教学目标（G1~G4），对应 config/goals.yamlExcel 源文件
knowledge_basedBOOLEAN 是否为知识库依赖型问题（TRUE=需要查KB才能回答）生成时自动判定
adversarial_typeVARCHAR(32) 对抗性类型：越狱 / 角色扮演 / 敏感话题 / NULL（非对抗）对抗性问题生成器
source_documentVARCHAR(256) 来源 Excel 文件名Excel 文件名
source_sheetVARCHAR(128) 来源 Excel 工作表名Excel 工作表名
source_excerptTEXT 原文摘录，便于审核时追溯Excel 单元格原文
statusVARCHAR(16)INDEX 审核状态：pending → approved / rejected前端 QA 管理页操作
reviewer_notesTEXT 审核备注，如"人工审核通过"前端 QA 管理页填写
approved_atDATETIME 审核通过时间系统自动记录
turnsTEXT 预设的多轮追问（JSON 字符串）QA 生成器
created_atDATETIME 创建时间系统自动
updated_atDATETIME 最后修改时间系统自动
这条数据怎么产生的？
① 用户在前端「QA 管理」页点击 "从Excel生成QA" → 后端调用 LLM 读取 Excel 生成 QA → 写入此表（status=pending）
② 用户逐条审核，点击 "通过" → status 变为 approved → 此条 QA 可被测试使用
③ 用户点击 "拒绝" → status 变为 rejected → 不会被用于测试

3.3 test_scenarios — 测试场景

用途：一次测试会话中有 N 个问题，每个问题对应一条场景记录。是 test_sessions 的子表。

列名类型标签含义数据来源
idCHAR(36)PK内部主键系统自动
session_idCHAR(36)FKIDX所属测试会话 → test_sessions.id系统关联
scenario_indexINT场景序号（1, 2, 3...），第几个问题系统按顺序
qa_pair_idCHAR(36)FK使用的 QA 对 → qa_pairs.id从 qa_pairs 随机抽取
statusVARCHAR(16)场景状态：pending → running → success / error系统自动
errorTEXT如果出错，记录错误信息系统自动
full_conversationTEXT完整对话文本（人工可读）系统拼接所有轮次
created_atDATETIME创建时间系统自动
updated_atDATETIME最后修改时间系统自动
数据流：TestRunner 从 qa_pairs 表中随机抽取 N 条已审核(approved)的 QA → 对每条 QA 创建一个 test_scenario → 每场景下发起多轮对话。

3.4 conversation_turns — 对话轮次

用途：一个场景中有多轮对话（提问→Agent回答→追问→再回答...），每一轮存一条。是 test_scenarios 的子表。

6. 数据产生链路总结

6.1 从用户点击到 MySQL 落库的完整链路

👤 用户 在前端点击"开始测评"
  ↓
📡 前端 POST 请求到后端
  ↓
🖥️ FastAPI 接收请求，在后台线程启动 TestRunner
  ↓
🎲 TestRunner 从 qa_pairs 随机抽取 N 条 approved QA
  ↓
💬 对每条 QA：发送问题给 HiAgent API → 获取回复 → 对话记录写入 conversation_turns
  ↓
🔍 边界检测：去火山引擎 KB 检索 → 记录写入 kb_retrieval_logs
  ↓
📏 L1 规则层：关键词匹配/结构检查/延迟检查/安全检查 → 写入 eval_traces.l1_*
  ↓
🧮 L2 算法层：语义相似度(embedding)/KB覆盖度 → 写入 eval_traces.l2_*
  ↓
⚖️ L3 LLM Judge：3 个 Judge 并行打分 → 每人一条写入 judge_decisions → 汇总写入 eval_traces.l3_*
  ↓
📊 融合评分：30% L1 + 70% L3 → 写入 eval_scores（8 维度）
  ↓
📋 生成报告：聚合所有场景 → 写入 reports
  ↓
📡 WebSocket 实时推送每一步事件 → 前端实时展示
  ↓
👤 用户 在前端看到完整的评测过程和最终得分

6.3 用 Adminer 验证数据流的典型场景

实战场景：你想确认一次评测是否成功入库。
  1. 打开 Adminer → 选择 test_sessions 表 → 按 created_at 倒序 → 找到最新一条记录，确认 status=success
  2. 点击该记录的 id → 跳转到 test_scenarios 表 → 查看有几个场景
  3. 点击某个场景的 id → 跳转到 conversation_turns → 查看 Agent 的每一轮回复（response_text）
  4. 回到场景 → 查看 eval_scores → 看到 8 个维度的具体得分
  5. 查看 eval_traces → 看到 L1/L2/L3 全过程（关键词命中哪些、Judge 原始 prompt 是什么）
  6. 查看 judge_decisions → 看到 3 个 Judge 各自打了多少分，谁的评分被排除了
这就是 Adminer 的核心价值——让你"看见"每一次前端操作在数据库中留下的完整痕迹。

7.1 Token 成本追踪

文件作用
src/token_tracker.pyToken 估算引擎：中英文自适应字符→token 转换 + DeepSeek 定价计算
backend/models/test_session.pyConversationTurn 新增 5 字段：prompt_tokens, completion_tokens, total_tokens, cost_estimate, model_used
backend/models/eval_trace.pyEvalTrace 新增 3 字段：l3_total_prompt_tokens, l3_total_completion_tokens, l3_total_cost
backend/alembic/versions/0003_token_cost_tracking.py数据库迁移脚本

工作原理

两层追踪：

① Agent 对话层 — 每轮 conversation_turn 自动记录：
  · prompt_tokens = 估算(question + system_prompt)
  · completion_tokens = 估算(Agent 回复)
  · cost_estimate = prompt_tokens / 1M × $0.14 + completion_tokens / 1M × $0.28

② Judge 评分层 — eval_traces 汇总所有 Judge 的成本：
  · l3_total_prompt_tokens = Σ 每个 Judge 的 prompt tokens
  · l3_total_completion_tokens = Σ 每个 Judge 的 completion tokens
  · l3_total_cost = Σ 每个 Judge 的调用成本

定价基准：DeepSeek 官方定价 — input $0.14/1M tokens, output $0.28/1M tokens
回退策略：若 API 未返回真实 usage.token_count，自动用字符数估算（中文 ~1.5 char/token，英文 ~4 char/token）

7.2 API 速率限制

文件作用
backend/middleware/rate_limit.py滑动窗口速率限制器 + FastAPI 中间件

限制规则

路径限制窗口原因
/api/* (全局默认)120 req/min60s防止滥用
/api/tests/run5 req/min60s评测启动是昂贵操作（LLM + KB + Playwright）
/api/qa/generate3 req/2min120sLLM 批量生成成本控制
/api/web-eval/run5 req/2min120sPlaywright 浏览器资源消耗
/api/kb/search30 req/min60s火山引擎 KB API 调用频率

工作原理

滑动窗口算法 (纯内存，无 Redis 依赖)：
① 每个请求到达时，按 IP 提取 client_key
② 清理窗口中过期的时间戳
③ 若窗口内请求数 ≥ 上限 → 返回 429 Too Many Requests + Retry-After 头
④ 若未达上限 → 记录时间戳，放行

响应头：每个 /api/* 响应都携带 X-RateLimit-Remaining，前端可据此调节请求频率
线程安全：threading.Lock 保护共享的 hits 字典

7.3 统计显著性检验

文件作用
backend/services/report_service.pycompare_reports 增强版：均值 · 标准差 · 变异系数 · Cohen's d 效应量 · 置信度

统计指标

指标算法输出需要
变异系数 (CV)σ / μ置信度标签：🟢高 (CV<0.10) / 🟡中 (CV<0.25) / 🔴低 (CV≥0.25)≥3 报告
Cohen's d(mean_best − mean_worst) / pooled_sd效应量：可忽略 / 小 / 中等 / 大 / 非常大≥3 报告
均值 + 标准差Σx/n, √(Σ(x-μ)²/(n-1))每个维度的 mu ± sigma≥2 报告
max_deltamax(vals) − min(vals)维度最大分差 (原有指标，保留)≥2 报告
纯 Python 实现，无 scipy 依赖：所有统计量均手动实现（_mean, _stdev, _cohens_d），避免增加依赖。
Cohen's d 解读：|d| < 0.2 = 可忽略 · 0.2~0.5 = 小 · 0.5~0.8 = 中等 · 0.8~1.2 = 大 · > 1.2 = 非常大
变异系数解读：CV < 0.10 = 评分高度一致 (Judge 稳定) · CV ≥ 0.25 = 评分波动大 (需关注)

7.4 Redis 缓存层

文件作用
backend/services/cache_service.py评估结果缓存：Redis (优先) → 内存 LRU (回退)

两级缓存策略

等级后端容量TTL用途
L1 — 评估结果Redis → 内存 LRU512 keys24h相同 (question, golden_answer, model) 的评分结果直接返回缓存，避免重复 LLM Judge 调用
L2 — Dashboard内存 LRU 专用32 keys30sDashboard 汇总统计 (total_tests, avg_score, trend...) 短时缓存，减少数据库查询

缓存 Key 设计

评估结果 Key：eval:SHA256({question, golden_answer, model, dimensions})[:16]
→ 相同问题+答案+模型的评估结果自动复用，避免重复 Judge 调用

Dashboard Key：dash:MD5(endpoint + params)[:12]
→ 30 秒内相同 Dashboard 查询直接返回缓存

自动回退：
  · 若 REDIS_URL 环境变量已配置且 Redis 可用 → 使用 Redis（跨进程共享、重启不丢失）
  · 若 Redis 不可用 → 自动回退到线程安全的内存 LRU 缓存
  · 无需 Redis 也能正常运行（零配置启动）
